## 活体验证记录（2026-09-09，本机直连）

探针 = 一次性脚本直接驱动 `src/core` 真实实现（真 fetch / 真 DNS / resolveConfig 默认值），关键结论：

- **实跑成功（12）**：bing（`b_algo` 锚点稳定，5 条 402ms）、anysearch（键树取证修正 answer 预期）、keenable（MCP 文本块锚点与解析一致；week 窗 5/5 命中窗内）、arxiv（submittedDate 12 位戳生效、3s 节流下正常）、openalex、crossref、pubmed（两步链）、stackoverflow、hn（numericFilters epoch 界精确）、npm、bilibili（-412 未触发）、web 引擎链整跑（bing 胜出 1789ms，degraded 注记路径正确）。
- **实现级修正（3）**：europepmc 响应形状 `resultList.result`（原误 `hits.hitList` → parse_failed 实锤后修复复跑通过）；bing `filters=ex1:"ezN"` 判零效果 → 删映射并 `supportsTimeRange: false`；anysearch `content` 作 snippet 回落。
- **read_source 冒烟（3/3）**：example.com 抽取 + artifact 落盘；arxiv abs 页 3096 字符抽取（文件名 `20260909-110926-arxiv.org-c29fa68b.txt` 形态契约吻合）；`169.254.169.254` → `unsafe_target` 拒绝（SSRF 活体验证）。
- **本机网络不可证（7 源 + searxng 全实例）**：ddg / ddg-lite / wikipedia / v2ex / reddit / github / searxng——分两层成因：**① hosts 劫持**（Steam++ 写入 `C:\Windows\System32\drivers\etc\hosts`：`api.github.com`/`github.com` 等 → `127.0.0.1`，Node 默认解析走 hosts → 连到本机 443 服务出现 `UNABLE_TO_VERIFY_LEAF`；同 hosts 块还含 steam/youtube/huggingface）；**② 网络层 DNS 污染**（ddg/wikipedia/reddit/v2ex 不在 hosts，本地解析非确定性返回经典伪造答案池 IP 或超时：`html.duckduckgo.com → 157.240.1.9`、`zh.wikipedia.org → 31.13.94.10`（Facebook 段）、`old.reddit.com → 104.244.42.197`（Twitter 段）、`www.v2ex.com → EAI_AGAIN`；对照组阿里 DoH 亦返回同池假值（duckduckgo→108.160.170.43 等）——污染在更上游，DoH 只保护最后一公里）。系统 DNS 为校园网递归 `202.118.66.6`。直连对照与插件跑签名一致 → **实现未判负，请求构造与出站参数经 out-bound 记录核实正确；换净网络/代理 TUN 复测**。
- **bing 幸存解释**：`www.bing.com` 走微软国内 CDN（`china.bing123.com → 202.89.233.x`），本地解析与 DoH 一致，不在伪造名单 → 引擎链默认首选在本环境实测可用。
- **SKIP（4 key 引擎）**：tavily / exa / perplexity / deepseek-official 未持 key（探针不读 DSH 凭据中心）；参数构造按 API 文档实现，持 key 环境复测。
- **bing 时间窗证据**：`q=大语言模型 最新进展` 与长尾 `q=python asyncio tutorial` 各跑 none/ez1/ez2/ez3 四组——host 集逐组相同 → filters 参数在 www.bing.com（zh-CN market）不生效。

## 活体验证记录 · 复测（2026-09-18，经 DSH 宿主诊断通道）

探针与首轮的**不同**：本轮不用裸 node 直驱 `src/core`，而是对**运行中的 test 实例**（0.1.2-rc.1，插件 `link:` 直挂）走插件自己的诊断通道 `POST /unity-search/test`（无浏览器验证通道取 token cookie，见知识库 `client/17` §7）——因此**凭据中心在场**（首轮 4 个 key 引擎的 SKIP 局面本轮被打散），且走的是与 `search_sources` 工具**同一条** host 侧 fanout/信封路径。查询词 `deepseek harness`、`maxResults=3`，逐源 24 条出站。

- **可用（14 条 = `web` 链 + 3 免 key 引擎 + 学术 5 + 平台 5）**：`web`（396ms，3 条，bing 胜出）、bing（838ms）、anysearch（2147ms）、keenable（741ms）；arxiv（967ms，1 条）、openalex、crossref、pubmed、europepmc 全部 `status: ok`；github（666ms，3 条）、stackoverflow（568ms，**可达但本次查询 0 命中**，与"不可达"不同类）、hn（2 条）、npm（3 条）、bilibili（3 条）。
- **网络层不可达（5）**：ddg（10499ms）、ddg-lite（10634ms）、wikipedia（10608ms）、v2ex（10660ms）、reddit（65ms）——统一 `network/fetch failed`；前四条 ~10.5s 是连接超时特征，reddit 65ms 是毒 IP 快速拒绝。
- **本机 DNS 复测（同系统解析器，与插件出站同径）**：`html.duckduckgo.com → 74.86.151.162`、`lite.duckduckgo.com → 208.101.60.87`（DDG 真值不在该网段）、`zh.wikipedia.org → 199.16.158.9`（Twitter 段）、`www.v2ex.com → 199.59.149.205`（Twitter/Bitly 段）、`old.reddit.com → 69.171.235.22`（Facebook 段）；直连对照 `curl --max-time 5` 两例均 `http=000` ⇒ 与首轮同池，**上游污染未变**。
- **首轮成因①已消失**：`C:\Windows\System32\drivers\etc\hosts` 现无任何生效映射（827 B 纯注释版，mtime 2026-09-17 23:45），Steam++ 的 github 劫持块已被清除 ⇒ **github 本轮转可用**，是首轮 7 个不可证源里唯二翻绿者（另一个是 searxng，因本轮未配实例仍不可判）。
- **凭据面（首轮 SKIP 项的对应面）**：tavily / exa / perplexity → `unavailable / credential not configured`（该 HOME 未录入 key；显式降级不静默，符合设计）；searxng → `unavailable / no instances configured`（默认关）；**deepseek-official → `http_4xx / DeepSeek API key is invalid (HTTP 401)`**——即凭据中心解析出了值但上游拒收（⚠ 作用域仅限 test 实例的 HOME；stable-dev 未测，不得据此判断生产 key 好坏）。
- **判定**：本机网络依赖的源里 **13 个源中 10 个可用**、10 个引擎中 3 个可用。不可用的 5 个**全部由本机网络层造成，无实现缺陷**（首轮结论维持）。引擎链在默认首选 bing 下不受影响；但 `ddg`/`ddg-lite` 在本机是 ~10.5s 的死重——bing 若失败，链会先白等一轮才轮到 anysearch（searxng 19ms 可忽略）。
- **路径归因（决定性证据，2026-09-21 追加）**：本机有一个在听的本地代理（`127.0.0.1:7897`；`HTTP_PROXY`/`HTTPS_PROXY` 均已设，`NO_PROXY=127.0.0.1,localhost,::1`；WinHTTP 层为 Direct）。经它访问这 5 个源的**真实端点**：`ddg-lite → 200`（21,574 B，含 `result-link` 锚点）、`wikipedia` API → `200`（7,924 B，含 `search`）、`v2ex` 热榜 → `200`（90,174 B）——HTTP 层三个转可达（⚠ 这一轮只是 curl 的标记检查，**不等于适配器能出结果**，下两条给出适配器级修正）；`ddg → 202` 且无 `result__a`（反爬挑战页）、`reddit → 403 Blocked 页`（出口 IP 被拒）——**这两个即便走代理仍不可用**。⇒ 直连失败的两层成因里，"出站路径"这层可被代理消解 3/5。
- **插件侧零改造的修复杆（实测）**：插件出站走全局 `fetch`，本身不涉及代理配置（`src/core/http.js` 与 `read/ssrf.js` 无 `proxy`/`ProxyAgent`/`HTTP_PROXY` 引用）。而 **Node v24.12.0 支持 `NODE_USE_ENV_PROXY=1`**：对照组（只设 `HTTP_PROXY`、不设该变量）`fetch('https://lite.duckduckgo.com/lite/?q=…')` → `fetch failed`；实验组（加该变量）→ `200 / 21,319 B`，wikipedia API 同组 → `200 / 7,924 B`。⇒ 给实例进程注入该环境变量即可让这 3 个源恢复（通道：启动器 instance `env_overrides`）。⚠ 该变量对**整个进程**的 fetch 生效（含 LLM 调用），副作用未测；更干净的是代理自身的 TUN 透明模式。
- **适配器级复跑修正了上一条的乐观结论（2026-09-21）**：探针从 curl 换成**裸 node 直驱 `src/core` 真实适配器**（与首轮探针同法）做 A/B——对照组（有 `HTTP_PROXY`、无 `NODE_USE_ENV_PROXY`）5 个源全部 `network: fetch failed`（与宿主内探针逐条吻合，可证探针保真）；实验组（加该变量）得 `ddg → ok 3 条`、`wikipedia → ok 3 条（深度求索）`、`v2ex → ok 0 条`（**真空结果**：现拉热榜 9 条无一含 deepseek，非解析失败）、`ddg-lite → ok 0 条`、`reddit → http_4xx 404`。
- **由此暴露并修复一个真 bug**：`ddg-lite` 适配器原用「标记里第一个双引号串」当 href，而现行标记是 `<a rel="nofollow" href="//duckduckgo.com/l/?uddg=…" class='result-link'>`，取到的是 rel 值 `nofollow` ⇒ `extractRealUrl` 返回 null ⇒ **9 条结果被逐条静默丢弃**（`status: ok, items: 0` 且无任何 warning）。该源在本机一直不可达，故 bug 从未暴露；测试面同样缺 ddg/ddg-lite 解析用例（`source-parse.test.mjs` 原只覆盖 wikipedia/arxiv/openalex/v2ex/keenable/pubmed）。**修法**：按属性名取 `\shref=["']([^"']*)["']`，并新增「检出结果块却一条都提不出来」时的 warning（结构漂移显形，不再静默）。**修后同探针复跑 `ddg-lite → ok 3 条`**（消融：同环境同探针、仅解析改动，0 → 3），补两条回归用例（真实标记 + 静默守卫），单测 97 → 99 全绿。
- **修正后的可用性结论（经代理 + 修后）**：`ddg`(3 条) / `ddg-lite`(3 条) / `wikipedia`(3 条) / `v2ex`(可达且解析正常，本次查询真空) 四项可用；`reddit` 仍不可用（404/403，出口被 Reddit 拒，与网络层修复无关）。

## 实例级落地与全量回归（2026-09-21）

把上节的"修复杆"真正落到实例上并做全量回归：

| crossref | `GET https://api.crossref.org/works?query=…&rows=…&mailto={contact}`；UA 带 contact 进礼貌池；`sourceIds.doi` 取 `DOI`；`extra`：`author`、`container-title`、`is-referenced-by-count` |
| pubmed | 两步：`GET https://eutils.ncbi.nlm.nih.gov/entrez/eutils/esearch.fcgi?db=pubmed&term=…&retmode=json&retmax=…` 得 PMID 列表，`efetch.fcgi?db=pubmed&id=…&retmode=xml` 取题录（XML 解析）；url = `https://pubmed.ncbi.nlm.nih.gov/{pmid}/`；`sourceIds.pmid`；NCBI 匿名约 3 req/s（core 限速闸 1000ms 满足），条款建议带 `tool`/`email` 参数（复用 `contact`） |
| europepmc | `GET https://www.ebi.ac.uk/europepmc/webservices/rest/search?query=…&format=json&pageSize=…&resultType=core`；JSON 结果路径 = **`resultList.result[]`**（活体 2026-09-09 修正，首版误写 `hits.hitList` 已修）；条目无 `pubDate`，日期取 `firstPublicationDate` → `pubYear` 兜底；`sourceIds.doi`/`pmid`；`extra`：`isOpenAccess`（Y/N）/`pmcid`/`journalInfo`；landing url 优先级 DOI > PMC > PMID；OA 全文/PDF 存在性入 `extra`，不自动抓取（有界原则） |

去重跨源主键 = DOI → arXiv id → 规范化 URL → 标题+首作者（规则归「检索核心与信封契约」）；pubmed 与 europepmc 的重叠条目经 DOI 或规范化 URL（`pubmed.ncbi.nlm.nih.gov/{pmid}/`）键在去重层合并。学术条目 `uncertainty` 恒定标注"仅元数据/摘要级"。

## 失败语义

- 所有适配器把上游非 2xx、超时、解析失败归一为 `SourceOutcome.error`（code 词汇表归「检索核心与信封契约」），不抛出。
- 解析失败的判定：HTML/JSON 结构不含任何可识别结果块；空结果（结构正常、零条目）不是失败。
- 抓取类引擎（bing/ddg/ddg-lite）改版导致解析失效率高时，处置 = 引擎自然冷却 + 修复解析锚点发版；不做运行时自动切换实现。
